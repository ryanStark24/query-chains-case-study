UX · 02 — The problem

Where the existing tools stop

Before designing anything we established what a Salesforce developer actually does when something breaks, and what the incumbent tools do and do not answer. The competitive picture set the bar; the workflow gaps set the brief.

The workflow being replaced

Current statedebugging a failed transaction, before

The insight that shaped the product: the expensive part is not any single step, it is the switching. Three of those four surfaces already exist in the browser the developer is in. Putting them one keystroke apart, sharing one session, removes the loop rather than speeding it up.

Competitive analysis

The reference point is Certinia's Apex Log Analyzer — free, open source, and the de facto standard for Salesforce log analysis. It is a genuinely good tool, and being honest about where it wins mattered more than listing where we differ.

Where we chose not to compete

A flame chart is expensive to build well and already exists. Spending the effort there would have produced a worse copy of a good tool. The gap worth filling was the one nobody had filled.

Where the gap actually was

Every viewer shows you the log. None of them tell you what went wrong. "101 SOQL queries — 8× from line 47" is a different product from a timeline, and it is the answer to the question people actually open the log with.

Constraints discovered in research

20 MBlog ceiling

Salesforce caps a single debug log at 20 MB and deletes 200 kB blocks to stay under it. Any analysis of a large log may be analysis of a fragment — which the interface has to admit.

24 hoursretention

System debug logs are kept for 24 hours. Anything worth returning to has to leave the platform, which is why downloading a log is a first-class action.

MV3no remote code

Manifest V3 forbids remote script execution. Every drop-in analytics, feedback or error-reporting widget is blocked by CSP — which forced a stricter privacy posture than we would otherwise have designed.

Decision
Study the tools people already use before proposing a replacement, and name what each one genuinely does well.
Evidence
Every existing viewer reports facts and leaves the diagnosis to the reader; every access answer is assembled by hand across several Setup pages.
Result
A thesis narrow enough to build against — answer the question, do not display the data.

UX · 03 — Direction

The rules chosen in response, and what enforces each one

Not aspirations pinned to a wall. Each is enforced by a test that fails, a flag that refuses, or a review rule — and each exists because its absence caused a specific problem.

Motion means data

Every animation in the live console is driven by an arrival. Nothing loops on a timer. The platform-events monitor pulses when an event actually lands, and sits still when the stream is quiet — so a subscribed-but-silent stream is visibly different from a busy one, and a dead stream is visibly different from both.

A decorative two-second interval on a chart window would keep sliding. It looked alive over a stream that had been dead for an hour. A decorative pulse is not neutral; it actively lies.

Density is a feature, not a style

The debug-log list shows one line per log — time, operation, duration, size. A stacked three-line entry puts about six logs on a screen. Debugging is a scanning task: you are looking for the one run that failed, and six-at-a-time turns that into a paging exercise.

Row height and type scale are fixed in the console layer and are identical across light and dark. Density is not a knob that varies by theme, because the thing that makes a console a console is information-per-screen.

Light mode is designed, not inverted

The token layer redefines the full palette per theme — every surface, ink and accent value has a light and a dark definition. That is the substrate. What is worth stating is narrower: within the live console, whose layout and density are shared byte-for-byte across themes, exactly three properties are allowed to differ, and each is a deliberate perceptual correction rather than a value flip:

PropertyLightDarkWhy it differs
Surface stack Rows are the brightest plane; the rail recedes Rows are darker than the rail Content advances in both, by opposite means. Inverting the dark values would push the navigation in front of the data.
Arrival flash 10% alpha, peaking at 24% 16% alpha, peaking at 42% Vermillion on near-white is far more assertive than on near-black. Equal alpha shouts in light and whispers in dark.
Live indicator oklch(45% 0.14 150) oklch(72% 0.15 150) The dark-mode green fails AA contrast on a light pill, and the reverse.

Everything else in the console — geometry, spacing, row height, type scale — is shared. If a theme needs a different layout to work, the layout is wrong. Colour values legitimately differ everywhere; structure never does.

Colour is signal; the accent is the only saturated thing

Vermillion marks liveness and recency. Semantic colours (error, warning, success) are separate from it and never used decoratively. Everything else is the neutral graphite ramp at hue 250 — a grey with a slight cool bias, chosen rather than inherited.

Severity is never carried by colour alone. A finding card has a left stripe and a text label, because roughly one man in twelve cannot rely on the stripe.

Say what went wrong, not what happened

Most log viewers report facts and leave the diagnosis to you. The analyzer names the problem: not Too many SOQL queries: 101 echoed back, but that plus the correlation — 101 queries, 8× from source line 47 — which is the difference between restating the error and pointing at the loop.

Confidence is always reported. A rule that infers by correlation says likely, never certain. A diagnostic that is confidently wrong is worse than no diagnostic, because it gets trusted.

An incomplete answer must say so

Salesforce truncates its own logs at 20 MB by deleting 200 KB blocks. Analysing a truncated log and reporting "no exceptions found" is actively misleading — the exception may be in the removed region. The analyzer detects Salesforce's truncation marker, and separately reports when its own parse budget was hit.

"Not found" and "not looked at" are different answers. Any surface that cannot tell them apart is a surface that will eventually mislead someone at the worst possible moment.

Destructive actions are confirmed, and the confirmation is specific

Every write to a verified production org requires explicit confirmation. The guard resolves sandbox status from the authoritative Organization.IsSandbox, never the hostname heuristic, and treats unknown as production.

Confirmations name what will happen: which record, how many rows, whether a log purge covers your logs or the whole org's. A generic "are you sure?" trains people to click through.

The design system is enforced by tests

Three gates run on every commit: a CSS line ratchet that can only be raised deliberately and with a written reason, an accessibility gate over the shipping surfaces, and an audit that keeps business logic on the cross-browser browser.* namespace. A principle nothing enforces is a preference.

Decision
State each rule as something a machine can check, not something a team can intend.
Evidence
Every principle here is backed by a test that fails, a flag that refuses, or a review rule — not by a poster.
Result
Rules that survive contact with a deadline, because breaking one breaks the build.

UX · 05 — Designing it

Four directions, one chosen, and why

The Events and Logs surfaces were the weakest part of the product: they worked, but they had no design of their own. Diagnosing why came before drawing anything, and the diagnosis turned out to be structural.

The root cause

There was no stylesheet for these surfaces. They borrowed the builder's — a design system built for composing a query, where the interface should hold still while you think. These surfaces do the opposite job: you are watching something, and the interface should react. They were never designed; they were assembled from the builder's parts, and they looked it.

Risks named before building

Density drift

Dropping a new visual language onto unchanged row heights produces a recoloured version of the same layout. The row height and type scale are the deliverable; the colours are not.

Reduced motion

Every liveness cue needed a non-motion equivalent, or the feature disappears for users who disable animation. The pulse becomes a static filled dot; the flash becomes a persistent left border.

Panel width

The console assumes horizontal room. At the 320px floor the rail collapses and the payload column truncates rather than wraps — wrapping breaks the fixed row height, which breaks virtualization.

Unverifiable liveness

A Developer Edition org publishes nothing, so none of this could be judged. A synthetic event harness had to be built before the design could be evaluated at all.

Decision
Name the risks before building, so the ones that matter are designed against rather than discovered.
Evidence
Density, reduced motion and the 320px panel floor were each written down as a way to fail before a line of the redesign was written.
Result
Row height and type scale became the deliverable; the palette was the easy part.

UX · 06 — The system

Two hue angles, three typefaces, one spacing rhythm

The entire palette derives from two hue angles held in custom properties. Changing --sfqc-hue-brand re-tunes every accent in the product at once — which is how the user-facing accent picker works, with no per-component overrides anywhere.

The problem

A Salesforce developer debugging a failed transaction has three tools open: Setup for logs, a query editor, and the record itself. None of them talk to each other, all of them lose your place, and the log viewer shows a wall of text with no diagnosis.

The interface is being read under pressure, by someone who already knows something is broken. Every screen has to answer a question faster than the tab they would otherwise switch to.

The constraint that shaped it

Authentication piggybacks on the browser session the user already has. No OAuth dance, no stored credentials — but it means the session cookie exists inside the extension, and must never leave one specific context.

That boundary is not a footnote. It determines the process model, the message protocol, and what each surface is even allowed to know.

The trust boundary

Process topology the architecture in one picture

Why it leads: for a tool whose defining property is that credentials never cross a boundary, the topology is the thesis. An exact-host assertion refuses any request whose URL is not on the org's own instance host, before the call is made — a suffix allow-list would have been an exfiltration path.

Internal architecture

Query Chains is a Chrome Manifest V3 extension for exploring Salesforce data with SOQL and SOSL. The whole design turns on one constraint: the Salesforce session token lives in an HttpOnly cookie, so only a context holding the cookies permission can read it. That single fact decides which process does what, what may cross the message bus, and what is allowed to be written to disk.

Process model

Five kinds of JavaScript context ship, declared in the manifest. They do not share memory; everything between them is message passing.

Service worker
The only privileged context. It reads the sid cookie, holds every session in memory, owns IndexedDB as sole writer, and makes every HTTP call to Salesforce. It is also the only place that may reach for the raw chrome.* namespace (along with the content script) — everywhere else uses webextension-polyfill's browser.*, enforced by a build-time audit described in the UI section. Being an MV3 worker, it can be evicted at any moment, so anything that must survive eviction is either in chrome.storage.session or re-derivable from the cookie.
Content script
Injected at document_idle into *.my.salesforce.com, *.lightning.force.com and *.salesforce.com. It does two small things and nothing else: it infers the org identity from window.location.hostname and fires REPORT_ACTIVE_ORG at the service worker, and it grafts a style-isolated edge launcher into a shadow root on the page. It never touches the session — it structurally cannot, because sid is HttpOnly. Its notify() helper guards on chrome.runtime?.id before sending, because after an extension reload the old content script's runtime is invalidated and sendMessage throws synchronously, so an attached .catch() never runs.
Builder tab
The full workbench: a normal extension page opened in its own tab. Multi-tab SOQL/SOSL authoring grouped by org, results grid, record editing, export, saved queries. The service worker keeps a per-window singleton registry so exactly one builder tab exists per Chrome window.
Side panel
Registered as side_panel.default_path. A narrow companion surface that follows whatever Salesforce page is in the active tab.
Two standalone mini apps
A platform-event monitor and a debug-log analyzer, each its own extension page in its own tab. They are deliberately not builder modes: the product fixes the builder at Query and Chain (design decision DD-01), and both of these tools want the whole window.

There is no popup. The manifest's action block has no default_popup; clicking the toolbar icon opens the builder directly through action.onClicked in the service worker, which also forces Chrome's openPanelOnActionClick off so a stale profile setting cannot hijack the icon. Two keyboard commands are declared: Ctrl+Shift+Q opens the builder, Ctrl+Shift+P opens the side panel.

Requested permissions are cookies, storage, downloads, alarms and sidePanel. Host permissions cover *.salesforce.com, *.force.com and *.salesforce-setup.com — the last because Salesforce's 2024–2025 Setup isolation can leave the Setup domain holding the only fresh session. incognito is split and the minimum Chrome version is 116.

Session and authentication

There is no OAuth dance and no stored refresh token. The extension reuses the session the user already has in the browser, which is why it works the moment you are logged into an org.

The session reader — the only code permitted to touch cookies — reads the sid value. The subtlety it exists to handle is that Salesforce sets sid on several hosts and they may hold different tokens. readSidCookie() therefore derives up to three candidate hosts from the org hostname — the API host (*.my.salesforce.com), the Lightning host, and the Setup-isolation host — reads sid from each, and picks the cookie with the latest expirationDate, because that is the currently active session. The resulting instanceUrl is always pinned to the .my.salesforce.com host, since that is the REST API endpoint. The org id is the leading segment of the cookie value, before the first !.

The my.salesforce.com cookie can be a stale pre-Lightning token or missing entirely — Trailhead Playgrounds routinely exhibit this — which is exactly why the freshest-expiry rule beats picking a single canonical host.

Sessions are cached by the session manager in a plain module-level Map, keyed by API host, with a 30-minute TTL (SESSION_CACHE_TTL_MS, one of the shared tuning constants). The constant states the rule directly: tokens live only inside the service worker's memory, are never persisted, and are never returned across the message bus. The reasoning is that chrome.storage.* is readable from every extension surface and from restored worker state, which widens the exposure surface for no gain. If the worker is evicted, the next getSession() simply re-reads the cookie — which requires the user to still be logged in, the same posture as before, minus a persistence layer to leak.

The consequence for UI code is structural: no surface can fetch a session and call Salesforce itself. It must ask the service worker to perform the call.

The exact-host guard

Every outbound request goes through sfFetch(), the single outbound wrapper, which calls assertSalesforceOrigin(url, instanceUrl) before attaching the bearer token. The guard is deliberately strict:

export function assertSalesforceOrigin(url: string, instanceUrl: string): void {
  let parsed: URL;
  try {
    parsed = new URL(url);
  } catch {
    // Relative path — always resolved against session.instanceUrl, so safe.
    return;
  }
  if (parsed.protocol !== 'https:') { /* SF_FETCH_HOST_DENIED */ }
  const instanceHostname = new URL(instanceUrl).hostname;
  if (parsed.hostname !== instanceHostname) { /* SF_FETCH_HOST_DENIED */ }
}

Note what it is not: it is not a suffix allowlist. The comment above it explains why. A saved chain may target a different Salesforce tenant, and *.force.com is a shared suffix — a suffix check would let a crafted chain exfiltrate a live bearer token to another org. The token goes to the exact hostname of the active session's instanceUrl, or nowhere. Anything genuinely off-org must go through a Salesforce Named Credential, which is resolved server-side inside Apex, so the token never leaves.

Both failure paths throw SFApiError with code SF_FETCH_HOST_DENIED and HTTP 403. This is defense in depth, not the primary control — the primary control is that no other context ever holds a token to misuse.

A second guard sits on the write path. A production-write guard refuses mutating operations against a production org unless the caller passes confirmedProdWrite: true. Two details are load-bearing. First, an unidentifiable org is treated as production (isProdOrg returns true for null) — fail-safe, never silently write to an org you cannot name. Second, effectiveGuardOrg() refuses to trust the hostname sandbox heuristic: Developer Edition hosts look like sandboxes to a regex but report Organization.IsSandbox = false and really are production. When the verified value cannot be read it is null, and null must never fall back to the heuristic.

Message protocol

All cross-context traffic is a single typed envelope, defined once in a shared module. MSG is a frozen constant map of roughly 89 message names — RUN_QUERY, DESCRIBE_OBJECT, LIST_ORGS, FETCH_NEXT_RECORDS, CANCEL_QUERY, the chain family, the debug-log and platform-event families, and so on. The union of its values is the MessageType type, so a typo in a message name is a compile error rather than a silent no-op.

export type MessageType = (typeof MSG)[keyof typeof MSG];

export interface Envelope<T extends MessageType = MessageType, P = unknown> {
  type: T;
  payload: P;
  requestId?: string;
}

export interface Response<T> {
  ok: boolean;
  data?: T;
  error?: { code: string; message: string };
  /** Friendly classified error shape — populated by the SW alongside `error`. */
  classified?: ClassifiedError;
}

Each message then gets a named pair, so payload and result are checked at both ends:

export type GetRecordMsg = Envelope<
  typeof MSG.GET_RECORD,
  { orgHostname: string; sobject: string; id: string;
    apiVersion?: string; fields?: string[] }
>;
export type GetRecordResponse = Response<{ record: Record<string, unknown> }>;

Two conventions run through the payloads. Every org-scoped message carries an orgHostname rather than a session — the worker resolves the session itself. Every mutating message carries an optional confirmedProdWrite?: boolean, which is what the production guard reads.

UI surfaces never call browser.runtime.sendMessage directly. They go through a typed client wrapper, whose private send() races the message against a timeout:

const DEFAULT_TIMEOUT_MS = 30_000;

async function send<T>(
  type: MessageType,
  payload: unknown,
  timeoutMs: number = DEFAULT_TIMEOUT_MS,
): Promise<Response<T>> { … }

The timeout exists because a hung service-worker handler would otherwise lock the calling surface forever with no error to show — two such silent hangs were the bugs that prompted it. Long operations opt out of the 30-second default: api.runQuery and api.runBulkQuery pass 600_000. The timer handle is retained and cleared in a finally block; without that, a response that wins the race still leaves a pending 10-minute timer alive, and a long session accumulates them. On timeout the rejection carries code: 'TIMEOUT'; a failed dispatch yields SEND_FAILED.

Not everything is request/response. The side panel opens a long-lived port named `${PANEL_PORT}:${windowId}` (PANEL_PORT = 'sfqc-panel'). The suffix is necessary because a side panel is an extension page, not a tab, so port.sender.tab is undefined and the worker has no other way to know which window a panel belongs to. The port exists to make the in-page launcher a toggle: chrome.sidePanel can open a panel but has no close API, so the worker pushes PANEL_CLOSE down the port and the panel closes itself. Broadcasts follow the same envelope shape — BULK_QUERY_PROGRESS for in-flight bulk jobs, PAGE_CONTEXT_CHANGED for panel auto-follow, ORGS_CHANGED for org discovery.

Concurrency

Salesforce enforces a concurrent-request cap per org, and tripping it produces failures that look like the extension is broken. Raw Promise.all over independent queries is therefore banned; every parallel path is gated by p-limit with a per-org ceiling:

export function concurrencyLimit(instanceUrl: string): number {
  return isSandboxUrl(instanceUrl) ? 4 : 20;
}

Twenty in production, four in sandboxes. Twenty rather than the platform's typical 25 leaves headroom so the extension does not consume the org's entire concurrency budget and starve the user's own Salesforce tabs. Four in sandboxes because sandboxes share pooled resources and have tighter limits. The same numbers appear as CONCURRENCY_LIMIT among the shared tuning constants. They are not user-tunable on purpose.

isSandboxUrl() is a hostname heuristic applied in order: a .sandbox. segment, a -- separator in the subdomain (myorg--uat.…), or a classic cs<digits> pod. It returns false for scratch orgs and Dev Hubs, whose instance URLs look like production. The content script hedges the other way for its own purposes and treats Developer Edition hosts as sandbox-like for concurrency, since both sit in the tighter bucket.

The sandbox heuristic is used for concurrency only. The production write guard explicitly refuses to trust it, because a Developer Edition org matches nothing here yet is a real production org — see effectiveGuardOrg above.

The limiter is applied in every executor — chain, DML, Apex and bulk, and on the UI side wherever the grid or a run comparison fans out. Superset decomposition is stricter still: its sub-queries run strictly sequentially.

Executing a query, end to end

  1. Typing. The editor is CodeMirror 6. Every document change writes the text into the Zustand store and runs a synchronous, network-free linter (trailing semicolon with a quick-fix, unbalanced parentheses, SELECT without FROM). Autocomplete is backed by a schema hook, which lazily fetches and dedupes describes; naming an object in the query warms its describe in the background. Completion is re-triggered manually after a trailing space, because CodeMirror's activateOnTyping does not fire on whitespace.
  2. Route selection. The run handler picks a path in a fixed precedence: Id-keyset chunking, then Bulk API 2.0, then superset decomposition, then a plain REST query. Bulk and keyset are never auto-armed — eligibility answers "can", not "should", and nothing in query text reveals the row count — so they require the manualExecutionControls toggle. A read-only plan chip mirrors the same precedence so the chosen route is visible before you run.
  3. Dispatch. The run hook mints a requestId, resolves the tab's effective org, strips comments and a trailing ALL ROWS, and calls api.runQuery(...) with a 10-minute timeout.
  4. Service worker. The RUN_QUERY handler registers its AbortController before the first await. This ordering is load-bearing: a CANCEL_QUERY arriving during session validation would otherwise find nothing in flight, return NOT_INFLIGHT, and the query would run anyway. It then resolves a validated session (60-second validation cache), re-checks the abort signal, and dispatches to query() or search().
  5. The call. query() chooses one of three endpoints — /query/, /tooling/query/, or /queryAll/. Tooling plus include-deleted throws INVALID_COMBINATION up front, because Salesforce has no /tooling/queryAll/ endpoint. The default API version is v62.0.
  6. Coming back. API usage rides home on the response, not a broadcast: sfFetch parses Sforce-Limit-Info: api-usage=n/m and the handler returns { result, limits }. Errors are classified into the classified field alongside the raw code, including edit-distance suggestions for misspelled field names. An AbortError becomes CANCELLED. An INVALID_TYPE failure triggers one automatic retry against the Tooling API, and the flip is persisted onto the tab if it succeeds.
  7. Rendering. The results grid renders a plain table below 200 rows and switches to @tanstack/react-virtual above it, with a fixed 34px row height and computed rather than measured sizes.
  8. More rows. Paging follows Salesforce's nextRecordsUrl through FETCH_NEXT_RECORDS; there is no separate queryMore verb. Appended pages increment the tab's API call count so the cost of a scroll stays visible.

The two heavy routes differ in shape. Bulk API 2.0 creates an async job, polls it, and downloads paginated CSV, pushing BULK_QUERY_PROGRESS broadcasts scoped by requestId; it has its own error codes (BULK_TIMEOUT, BULK_ROW_LIMIT, BULK_FAILED). Id-keyset chunking walks the object in primary-key order in 2000-row slices, which is what lets an unoptimized full-object extract return at all — at the cost that results come back in Id order, so a user's own ORDER BY cannot be honoured.

Superset decomposition (alias/CASE/UNION, same-object semi-joins, big IN lists, cross-object joins) runs entirely client-side. The service worker never sees superset syntax — the planner rewrites it into ordinary SOQL sub-queries, the runner executes them sequentially, and the combiner merges the rows locally. Constructs it cannot support are rejected before a single API call is spent.

State

The builder's single source of UI truth is a single Zustand store. It is a bare create<AppState>((set, get) => ({ … })) — no persist, no immer, no devtools, no subscribeWithSelector. Persistence is hand-rolled through paired load/persist helpers, which keeps the storage tier of each field an explicit, readable decision rather than a middleware config.

What it owns:

  • Shell — mode, theme, command-palette open state, the drawer and its stack.
  • Settings — API version, default export format, manual execution controls, the production-write guard mirror.
  • Orgs — active org, discovered orgs, aliases, API limits, session-expired flag, and the tooling/standard object name sets.
  • Query tabs — units keyed by id, their order, the active id, per-org tab groups, run progress, and recents.
  • Chain state — present but dark behind the release flag.
  • Caches — describes keyed ${orgHostname}::${sobjectName}, saved queries, and env/global variables.
  • Section state — per-unit inspector open/closed sections.

What it deliberately does not own is the more informative list:

  • Session tokens. The store never sees a sid. Every network call goes through the typed client to the service worker.
  • The authoritative describe cache. The store's copy is a session-scoped mirror; the comment reads // --- Describe cache (session-scoped; SW IDB is the persistent layer) ---. Two writers to one cache is a bug factory, so there is one writer and one mirror.
  • The authoritative production-guard setting. Also a mirror — the field is documented as a mirror of chrome.storage with the service worker as the authority. A security control that the UI can flip locally is not a control.
  • Result records of deleted tabs. Closing a unit strips its runtime status so stale records neither leak into memory nor resurface if a new unit reuses the id.
  • Single-surface widget geometry. Sidebar collapse and inspector width live in their own hooks with their own localStorage keys. The rule is about cross-component concerns; a value only one component reads does not belong in a global store.

The side panel and the two mini apps do not use the store at all. The panel entrypoint says so directly — it is a lightweight consumer surface with no builder store. It runs on its own hooks (usePanelContext, usePanelRecord, usePanelSchema, useRecordAccess) over the same typed client, with no polling: it fetches page context once on mount and then follows a service-worker broadcast. What it does share with the builder is the CSS design system and the API client — the two things worth sharing.

usePanelContext normalizes *.salesforce-setup.com and *.lightning.force.com to the *.my.salesforce.com API host before making any request, because the service worker keys sessions and describes on the API host. Without that rewrite a panel request made from a Setup page resolves no session and fails with NO_SESSION.

Design system

All visual constants live in one token stylesheet as CSS custom properties under the --sfqc-* prefix. Components read tokens; magic hex values in component CSS are not allowed. The system is called "Graphite & Vermillion", and its defining move is that the entire palette is generated from two hue angles:

--sfqc-hue-brand: 22;      /* vermillion / persimmon */
--sfqc-hue-neutral: 250;   /* cool blue-gray */

Every surface, border, text and brand colour is an oklch() expression referencing one of those two hues, which is why the whole interface retints coherently from a one-line change. OKLCH also makes lightness perceptually uniform, so a dark-mode variant is a lightness swap rather than a hand-tuned second palette.

Automated design gates

Design systems decay through accumulation: nobody adds 2000 lines of CSS, everyone adds twelve. Three gates run in CI to make that accumulation visible and deliberate.

The CSS ratchet

A ratchet is a ceiling that only moves one direction: down. The test walks every stylesheet in the token directory, sums their line counts, and asserts the total is at or below a hardcoded constant:

const CSS_LINE_CEILING = 12_973;
const INLINE_STYLE_CEILING = 665;

The number cannot rise by accident — raising it requires editing the constant, which shows up in review as an explicit decision. In practice the file has become a changelog: every adjustment carries a comment naming the feature surface that justified it and the before/after numbers. Migrating a component from a legacy stylesheet into the canonical layer pulls the total down, and the ceiling is then ratcheted to the new actual so the reclaimed budget cannot be silently spent. The largest single movement in the log is parking the Chain Mode UI, which removed 1,940 lines of chain stylesheet and dropped the ceiling from 14,342 to 12,400 — with a note that restoring the stylesheet means restoring the ceiling too.

The same file carries two more assertions. One restricts the two entrypoints to an allowlist of exactly three stylesheet imports — the tokens, the manifest, and the panel shell — so an ad-hoc stylesheet cannot re-enter through the side door. The other counts style={{ occurrences across production TSX. Some inline styles are unavoidable: a bar that is 73% wide because a governor limit is 73% consumed has no static CSS form, and a virtualizer's per-row translateY is computed at runtime. Static ones are not, and the ceiling captures the current total and only lets it fall.

The file names its own blind spot honestly: it walks the token directory only, so the console and panel stylesheets are not counted by the line ceiling. That is recorded in a comment as a real gap rather than a deliberate exemption. An audit that hides its own scope invites a reader to trust a guarantee it never made.

The accessibility gate

A source-level scan over the surfaces that actually ship — the panel, the mini apps, and the shipping builder surfaces (Query Mode, drawer, shared components, the settings/help/about overlays, palette, toasts). It parses JSX opening tags with a hand-written scanner rather than a regex, because attribute values contain > characters from arrow functions and a naive pattern truncates the attribute list, making every label after the first arrow function look missing.

Seven assertions, each requiring an empty findings list:

  • No native control (input, select, textarea) without an accessible name from aria-label, aria-labelledby, an id, or an enclosing <label>.
  • No onClick on a plain element that has neither a role nor a tab stop — the class of bug where a feature simply does not exist for keyboard users.
  • No native <select>. Its option list is drawn by the operating system and cannot be themed, so it renders a system-blue popup over the dark UI; a Select primitive exists for this.
  • No positive tabIndex — it reorders the whole page's tab sequence, not just the offending component's.
  • Every <img> has alt.
  • Every role="tab" reports aria-selected.
  • And, unusually, that CHAINS_ENABLED === false.

That last one is the interesting assertion. Chain Mode is excluded from the scan because it ships dark; including it would either block a release on unreachable UI or force the thresholds so high the gate stops meaning anything. But an exclusion that outlives its justification is worse than no gate, so the test asserts the precondition it depends on. Turn the flag on without auditing Chain Mode and this test fails loudly.

The polyfill audit — scripts/audit-raw-chrome.mjs

Walks every production source file and fails the build (exit 1) on any production source file reaching for the raw chrome.* namespace instead of webextension-polyfill's browser.*. Two directories are exempt as manifest-driven bootstrap glue: the service worker and the content script. Individual lines can opt out with an inline // audit-allow-raw-chrome marker, and the per-file exempt list is kept empty.

The rule exists so business logic stays portable — the repo also produces a Firefox build — and so callback-versus-promise inconsistencies do not leak into shared code. The success message names the exempt directories explicitly rather than claiming "no raw chrome.* usage in production sources", which would overstate a check that does not scan the background directory.

Accessibility commitments

Contrast. The target is WCAG 2.1 AA on all text. Building the palette in OKLCH is what makes that tractable, since the first coordinate is perceptual lightness — text and surface tokens can be reasoned about as a lightness gap rather than checked pair by pair. Non-text indicators are held to the 3:1 threshold too, and one case shows the care that takes: the toast chip is inverted (its background is the text colour), so a severity stripe tuned for light mode drops to roughly 1.7–2.5:1 in dark mode. Rather than accept that, dedicated --sfqc-toast-stripe-* tokens are pitched against the opposite theme's chip lightness in each mode. Severity is also never carried by fill alone — the log analyzer's finding cards use a left edge and a text label as well, deliberately spending more rules than a single-channel treatment would need.

Reduced motion. The token layer collapses --sfqc-motion-fast and --sfqc-motion to 0.001ms under prefers-reduced-motion: reduce, which handles everything token-driven. That is not sufficient on its own, so a global rule follows it:

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.001ms !important;
    transition-delay: 0s !important;
    scroll-behavior: auto !important;
  }
}

A handful of components hard-coded inline transition declarations, and an inline style outranks every stylesheet rule short of !important — so those animations ran regardless of the user's OS preference until this rule landed. Individual layers add their own reduced-motion blocks on top. The in-page edge launcher is a special case: it lives in a shadow root grafted onto Salesforce's own document and can inherit none of the extension's CSS, so the content script reads matchMedia('(prefers-reduced-motion: reduce)') in JavaScript and branches the stylesheet text it injects.

Keyboard reachability. Modal dialogs go through one shared useDialog hook, which implements the WAI-ARIA dialog pattern in full: Escape closes, Tab and Shift+Tab cycle within the container, focus moves in on mount preferring a [data-autofocus] element and falling back to the first focusable or the container itself, and focus returns to the invoking element on unmount. Fifteen-plus components use it. Non-modal popovers use a separate usePopover hook with Escape, click-outside, and focus return, whose documentation routes modal cases back to useDialog.

Shortcuts exist at every level: Ctrl+Shift+Q and Ctrl+Shift+P from the manifest, Cmd/Ctrl+K for the command palette and Cmd/Ctrl+1..2 for modes in the builder, Cmd/Ctrl+1..9 for panel destinations, and Mod+Enter to run a query. Two details are worth copying. The panel derives its shortcut range from the length of its tab list rather than hardcoding it, because a literal upper bound went stale the moment the rail grew and left the new surfaces keyboard-only in name. And the panel's /-to-search binding is suppressed while focus is in a text field, because / is valid SOQL syntax.

The command palette carries a related guard: an intentArmed flag means Enter does nothing until the user has typed or moved the selection with arrow keys, because an idle Cmd+K followed by Enter was firing whatever command happened to sit at index zero.

Asynchronous results are announced rather than silently swapped in: aria-live regions are used in the results table, the record editor, the subquery inspector, the query-plan panel, the toast host, and the shared live console.

Evidence

Result
No OAuth flow, no stored secret, and a trust boundary that the process model enforces rather than documents.

Two rendering traps, and their fixes

The infinite render loop

Find-in-log wedged the renderer. An effect called scrollToIndex with the virtualizer object in its dependency array — that object is new every render, so the effect re-ran every render, and scrolling caused a render.

Rule that came out of it: scrolling happens in the key handler, never in an effect.

Fixed row height is load-bearing

The virtualizer sizes rows from a constant. A wrapping cell gives rows variable heights, the estimate drifts, and the scroll position slides out from under the user as they read.

Hence: white-space: nowrap with truncation in every console row, including at the 320px panel floor where wrapping would be the obvious choice.

Decision
Find the actual ceiling instead of applying the standard remedy.
Evidence
The list was already virtualized; the cost was the parse, where a 40 MB log becomes 400,000 objects before a row renders.
Result
A bounded parse that states when it truncated, so no analysis silently reports on a fraction of a log.

Tech · 03 — Reliability & safety

This tool can delete production data

It edits records, deletes them, publishes platform events and purges debug logs org-wide. Every one of those is irreversible, and several affect users who are not the one clicking. Reliability here is not uptime — it is never doing something the user did not ask for.

Layers of defence

A destructive action, gated four times

Defence in depth is not decoration here. When Chain Mode was disabled, the interface was removed and the service worker kept rejecting chain-execution messages independently. Hiding a control is not a security boundary; refusing the message is.

The guard that heuristics broke

The production-write guard originally derived sandbox status from the hostname. Developer Edition orgs contain -dev-ed., so they were classified as sandboxes and writes saved with no confirmation at all — while the badge in the same interface correctly read "Production", because it used the authoritative value. Now everything reads Organization.IsSandbox, and unknown is treated as production. Never trust a hostname for a write decision.

Tech · 04 — Decisions

Five decisions, and what each one settled

Recorded with their reasoning, because the reasoning is the part that stops a future change from quietly undoing them.

Parking a finished feature

Chain Mode — a visual canvas for composing multi-step query workflows — was built, tested and working. It ships disabled, and its interface was removed from the bundle entirely.

The flag CHAINS_ENABLED had already made it unreachable, but the code was still downloaded by every user. Measuring the cut settled it:

React Flow disappearing was the surprise: it existed only for the chain canvas, so the real saving was nearly double the headline chunk. The test count dropping is not a regression — those tests covered the interface that left with it.

The important part is what stayed. The execution engine, the shared QueryUnit type, saved-chain storage and the service worker's refusal to run chains are all still there. Measurement before cutting showed QueryUnit is shared vocabulary — every executor Query Mode needs speaks it, across roughly 121 files — so removing it would have meant inventing a parallel type for no user-visible gain.

Restoring Chain Mode is a checkout from the parked branch plus a flag flip. That cheapness was the design goal; a "clean" removal that made the feature expensive to bring back would have been the worse engineering decision.

How a query actually runs

The path from keystroke to rendered rows crosses the trust boundary twice and never carries a credential back. Every branch below is a real decision point in the executor, not a simplification.

Disclosing exactly what the extension does

A privacy policy is a factual claim about behaviour, so it is written from the permission set and the message handlers rather than from a description of the product. It names the side-panel permission, record creation and deletion, platform-event publishing, org-wide log deletion, the streaming subscription and the Bulk API path — every capability that touches an org.

It is also precise about direction. The content script sends only the org hostname, derived from window.location.hostname; the page URL is read separately by the service worker through chrome.tabs.query. Those are different disclosures and the policy states them separately.

The policy lives in three places that must agree — the repository, a public copy the store listing points at, and an in-extension copy that ships with the build. Nothing enforces that agreement automatically, so a capability change means editing three files, and that is the failure mode the review checklist is written around.

Two verification layers, and a list of non-defects

Every release runs an automated gate — tests, typecheck, lint, build, and a raw-chrome.* audit — and a functional pass driven against a Developer Edition org with query-safe data. Neither substitutes for the other: the gate cannot see a control that renders but does nothing, and the functional pass cannot see a type that no longer compiles on a path it did not walk.

The functional plan carries a "do not report these as defects" list, because two behaviours look like bugs to a runner following steps and are deliberate:

The disabled Chain tab ignores clicks
While gated it is a native-disabled control with no routing attached, documented in the header component. The Coming Soon page is reached by URL instead.
Malformed SOQL shows no lint marker
The linter checks six specific shapes — trailing semicolon, unbalanced parentheses, SELECT without FROM, empty SELECT, COUNT(*), and FIND braces. General syntax is not among them, so silence is the correct answer.

A scenario is marked PASS only with direct evidence. Anything the runner cannot reach — an authenticated org from a headless environment, for instance — is recorded BLOCKED, never passed.

Building the harness the feature is judged against

A Developer Edition org publishes no platform events. The monitor's liveness behaviour — arrival pulse, row flash, follow-and-pause, drop accounting — has nothing to react to, so none of it can be seen or regression-checked by eye without a source of traffic.

The simulator injects synthetic events at the exact point a real batch lands, so everything downstream behaves identically. It writes nothing to Salesforce: publishing real events would need an event object to exist, would fire every downstream trigger in the org, and would put a "flood my org" button in a shipping product. It stays behind EVENT_SIMULATOR_ENABLED, off in packaged builds.

It proves the interface and proves nothing about the CometD connection, which sits upstream of the injection point. Stating that boundary matters more than the harness itself — a green simulator run is not evidence that streaming works.

Evidence

Decisions that a future change cannot quietly undo, because the cost of undoing them is written down.
